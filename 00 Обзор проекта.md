# StockFlow AI — обзор проекта

Веб-приложение (React + TypeScript + Vite + Zustand + Supabase) для складского учёта HoReCa, на сервере Vercel. **Не Telegram-зависимость** — Telegram сейчас один из способов открыть приложение, не архитектурная основа (уточнено пользователем 06.08.2026). В планах — нативные обёртки под Android (APK) и iOS. Папка `src/modules/tma/` в коде называется по историческим причинам ("Telegram Mini App") — переименование отложено, не срочно.

- **org_id:** `cf7e977a-1837-4f51-8851-e44f37e50edd`
- **Фронтенд:** деплой через Vercel при пуше в git (репозиторий `Psysapp/StockFlow`, домен `stock-flow-blond.vercel.app`) — **репозиторий доступен для клонирования с 18.08.2026** (см. GitHub PAT в credentials, отдельный от токена stockflow-notes)
- **Edge Functions:** деплоятся отдельно через Supabase Dashboard/MCP — НЕ через git-пуш автоматически
- **Sync Agent:** отдельная Node.js-программа на компьютере в заведении (репозиторий не в git, файлы передаются вручную)

## Видение продукта

AI-powered операционная система для инвентаризации в общепите — не просто счётчик остатков, а центральная платформа, объединяющая закупки, продажи, производство, аналитику и ИИ. Долгосрочная цель — стать "операционной системой" для управления складом HoReCa.

## Технологический стек

- **Frontend:** React, TypeScript, Vite, Tailwind CSS, Zustand, React Router
- **Backend:** Supabase (PostgreSQL, Auth, Storage, Edge Functions)
- **AI:** Gemini (основной), Groq (запасной провайдер)
- **Desktop-интеграция:** Node.js, Windows Service (NSSM)

Идёт работа над расчётным остатком (продажи + списания за вычетом уже отражённого в StoreHouse) — упирается в нерешённый вопрос связки "блюдо r_keeper → товар StockFlow" (пробовали GUID, не подтвердилось; ищем поле "Код r_keeper" по подсказке из документации — см. ## Правила работы

- **Замена файлов Sync Agent (`index.js`, `sync-catalog-api.js`) — копить изменения за сессию, отдавать одним файлом в конце.** Пользователь явно попросил (11.08.2026): не отдавать файл на замену после каждой отдельной правки — это заставляет несколько раз подряд заменять файл и перезапускать службу. Вместо этого — собирать все изменения за сессию/задачу, и только когда работа над этим направлением закончена (или пользователь явно просит) — предлагать один финальный файл на замену.
