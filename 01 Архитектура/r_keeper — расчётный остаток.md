# r_keeper — интеграция и расчётный (теоретический) остаток

Статус: **идея проработана архитектурно, реализация не начата.** Следующий шаг — проверить техническую доступность (см. "Технический доступ" ниже), потом продолжим.

## Исходная проблема (подтверждена документацией r_keeper, 06.08.2026)

r_keeper передаёт данные о реализации в StoreHouse **не мгновенно** — через утилиту QUSH, у которой три режима:

1. **Ручной импорт** — кто-то должен зайти и нажать "Запустить".
2. **Автоматический импорт раз в сутки** — в заданное время, за "сегодня/вчера/позавчера". Задержка до ~24 часов.
3. **"Онлайн списание"** — единственный близкий к реальному времени режим, опрос раз в **5 минут**.

Важный нюанс: даже импорт продаж ("заявка") сам по себе **не списывает товар** — нужна отдельно включённая настройка "Автоматическое списание", которая конвертирует заявку в реальные накладные, влияющие на остатки.

Источник: `https://docs.rkeeper.ru/rk7/7.7.0/ru/nastrojka-svyazi-so-storehouse-5-27849362.html`

## Идея (предложена пользователем 06.08.2026)

Подключить Sync Agent **отдельно, только на чтение**, напрямую к тому же источнику, что уже читает QUSH — не заменяя и не трогая существующую синхронизацию QUSH→StoreHouse.

**Формула:**
```
расчётный остаток = последний точный remain из StoreHouse (GRemns)
                     минус реализация из r_keeper, ещё не учтённая в StoreHouse
                     минус одобренные списания StockFlow, ещё не проведённые в StoreHouse
```

Продажи блюд переводятся в расход сырья через уже существующие техкарты (состав известен).

Это будет явно помечено как **оценка**, а не факт — витрина поверх официального remain StoreHouse.

Побочная ценность: сама разница между теоретическим и фактическим расходом — известный в ресторанном деле инструмент контроля потерь (соответствует пункту PRD "Loss prediction").

## Технический доступ — два возможных пути

**Qush_Manager → Файл → Связки с R_keeper → [открыть существующую связку] → вкладка "Базы данных" → раздел "r_keeper 7"**.

Подготовлен скрипт проверки: `probe-rkeeper-db.js` (использует `mssql`, нужно `npm install mssql`) — подключается к базе, выводит список всех таблиц + пробует прочитать TOP 3 из ORDERS/PAYMENTS/VISITS.

**Статус: пользователь пока не проверил на месте (не знает точно, что реально доступно).**

### Путь 2 — XML-интерфейс r_keeper (запасной)
Отдельный API у r_keeper (`https://IP:порт/rk7api/v0/xmlinterface.xml`), но:
- по умолчанию HTTP-интерфейс в r_keeper **выключен** — нужно включить в свойствах кассового сервера и **перезагрузить кассовый сервер** (риск для живой кассы);
- нужна отдельная настройка прав доступа, как в StoreHouse;
- есть тестовая страница для проверки запросов: `https://ip:port/webgui/iservxmltest.htm`.

Источники: `https://docs.rkeeper.ru/rk7/latest/ru/xml-interfejs-r_keeper-7-19605640.html`, GitHub `antonko/RK7Die` (пример клиента).

r_keeper и StoreHouse стоят на **том же компьютере**, что и Sync Agent (подтверждено пользователем) — доступ технически не требует новой сетевой инфраструктуры, независимо от выбранного пути.

## Логика избежания задвоенного вычитания списаний — разобрано подробно

Пользователь сам нашёл и продумал несколько реальных дыр в логике, каждая разобрана и закрыта:

### Проблема 1: "время последнего remain" как граница — неверный критерий
Первая версия идеи (авторства Claude) была ошибочной: считать, что всё созданное ДО времени снимка remain — уже учтено. **Опровергнуто пользователем**: снимок остатка отражает то, что бухгалтер реально ВНЕС, а не то, сколько времени прошло. Если бухгалтер не работал по выходным, новый (более поздний по времени) снимок в понедельник всё ещё не будет содержать субботние списания — простое сравнение по времени привело бы к ошибочному "прощению" ещё не учтённых списаний.

### Решение: сопоставление по факту наличия в реальных документах StoreHouse, не по времени
Читать реальные расходные документы StoreHouse (та же идея, что GDocs/GDoc0 для приходных — нужно будет найти аналог для расходных, вероятно другая битовая маска типа документа) и **сверять по факту**, а не предполагать по часам.

### Проблема 2: несколько идентичных списаний (тот же товар+количество)
Точное сопоставление "конкретная запись → конкретный документ" невозможно и не нужно. **Решение: сравнение по количеству, не по паре.** Если в StockFlow 2 неподтверждённых списания "курица 300г", а в StoreHouse нашёлся только 1 такой документ — подтверждённым считается меньшее число (1 из 2), какое именно из двух — не важно, они неотличимы по сути.

### Проблема 3: ~100 списаний за выходные, бухгалтер группирует по дате проведения (не по дате факта)
Если сравнивать "по дню" — ломается, когда бухгалтер заводит один документ с одной датой (например, датой понедельника) на все накопленные за выходные списания. **Решение: убрать "день" из группировки полностью**, сравнивать по товар+количество за широкое окно (например 2 недели), не по конкретной дате.

### Проблема 4: ложное совпадение (кто-то вручную списал ровно то же количество по другой причине)
Возможно, но **не критично** — ошибка не накапливается. Расчётный остаток строится каждый раз заново от последнего РЕАЛЬНОГО remain StoreHouse; временная неточность из-за ложного совпадения самоисправляется на следующей настоящей синхронизации остатков. Худший случай — временное небольшое искажение между синхронизациями, не постоянная порча данных.

**Возможные усиления точности (не обязательны, на будущее):**
- Сравнивать не только товар+количество, но и подразделение (Кухня/Бар), если видно в документе StoreHouse.
- Просить бухгалтера указывать ID из StockFlow в комментарии при ручном проведении — даёт 100% точное сопоставление, но требует человеческой дисциплины.

## ПРОРЫВ 16.08.2026 — XML-интерфейс r_keeper РЕАЛЬНО РАБОТАЕТ

После нескольких недель поисков — успешное подключение и получение живых данных.

**Ключевая ошибка, которая всё это время мешала:** мы были уверены, что HTTP Data Port = **8036** (настраивали его сами в самом начале). Оказалось — это было ошибкой (перепутали/неверно запомнили). **Реальный порт, прописанный в свойствах кассового сервера (Сервис → Станции и устройства → MDSERV → Свойства → HTTP Server) — 8086.** 8036 никогда не был настоящим портом, поэтому все прошлые попытки (сканирование подсети, ожидание перезапуска) не могли сработать в принципе — стучались не в ту дверь.

**Рабочая связка:**
- IP кассового сервера (MIDSERV): **192.168.1.137** (это тот же компьютер, где физически стоит касса с чековым принтером SAM4S — подтверждает раннюю догадку пользователя "может это сам r_keeper, где заказы пробивают?")
- Порт: **8086**
- **Обязательно HTTPS, НЕ HTTP** (`socket hang up` на HTTP, `200 OK` на HTTPS — самоподписанный сертификат, `rejectUnauthorized: false` в скрипте)
- Путь: `/rk7api/v0/xmlinterface.xml`
- Пользователь: `stockflow` / пароль `1337` (роль "StockFlow", привилегия HTTP Access — настроено ранее)
- `HTTP Bind Address` — пустой (слушает на всех интерфейсах, не только localhost)
- `Use Free Listen Port` — выключено (порт фиксированный, не меняется)

**Подтверждено реальными ответами:**
- `GetSystemInfo` — вернул версию сервера, NetName=MIDSERV, название ресторана "ХопМолт Паб", RestCode.
- `GetOrderList` — вернул РЕАЛЬНЫЕ заказы: Visit ID, Order ID, стол, официант (WaiterID/WaiterCode), суммы (OrderSum, ToPaySum), время открытия/закрытия (CreateTime/FinishTime), статус (Finished).

**Рабочий скрипт:** `/mnt/user-data/outputs/probe-rkeeper-xml.js` (обновлён с правильными IP/портом), запускался с компьютера Sync Agent через `node probe-rkeeper-xml.js`.

### Следующий шаг

`GetOrderList` даёт заказы на уровне сумм, но НЕ показывает состав (какие конкретно блюда). Нужно проверить `GetOrder` (по конкретному `guid` заказа) — должен вернуть позиции блюд внутри заказа. Это и есть последний недостающий кусок для реализации `rk_sales_history` (таблица уже создана, ждёт наполнения).

Полезный факт из истории: **лицензия по подписке нужна только для команд ЗАПИСИ** (SaveOrder, PayOrder и т.д.) — для чтения (GetOrderList/GetOrder) ограничений нет, что и подтвердилось на практике.



### ФИНАЛЬНОЕ ПОДТВЕРЖДЕНИЕ (тот же день) — GetOrder отдаёт состав блюд

`GetOrder` по конкретному `guid` заказа вернул РЕАЛЬНЫЙ список блюд внутри заказа — то самое последнее недостающее звено. Пример из теста (заказ №32867/1):

```xml
<Dish id="1005744" code="3266" name="POT5" price="45000" quantity="4000" .../>
<Dish id="1000728" code="2585" name="Гренки чесночные" price="31000" quantity="1000" .../>
<Dish id="1001626" code="926" name="Сэт из копченого сыра" price="59500" quantity="1000" .../>
```

Похоже на масштаб ×100 для цены (45000 → 450₽) и ×1000 для количества (4000 → 4 шт) — стандартная практика r_keeper. **Подтверждено ЧАСТИЧНО**: на всех протестированных блюдах (целые штуки — булочки, капучино, паста) деление на 1000 давало правильные целые числа. НЕ проверено на весовом/дробном блюде — при появлении такого в реальных данных стоит свериться вручную.

Также важно: блюда сгруппированы по `<Session>` (не по заказу целиком) — заказ может иметь несколько "сессий" (например, если гости доказывали позже) — при разборе XML нужно проходить по ВСЕМ `<Session>` внутри `<Order>`, не только по первой.

Исправлено: курсор двигается, только если ни одной ошибки не было за весь прогон.

**Проверенные вживую сценарии (все безопасны):**
- ✅ **Разделение счёта / перенос блюда на другой стол**: протестировано реальным переносом одной из двух одинаковых нулевых позиций на другой стол, оба стола закрыты. Результат — обе записались РОВНО по разу, задвоения нет. Технически: r_keeper создаёт НОВЫЙ `line_guid` для перенесённого блюда (не переносит старый) — но поскольку это реально два разных объекта в r_keeper, наш код корректно видит их как два разных факта, что и требовалось.
- ✅ **Стол дозакрыли позже / добавили позиции после первого закрытия**: по конструкции безопасно — используется ТОЛЬКО `FinishTime` (время закрытия), не время открытия; если стол переоткрыли и закрыли снова с более поздним временем — попадёт как "новый" заказ автоматически.
- ✅ **Много заказов закрылось одновременно**: обрабатываются последовательно, не параллельно — при очень большом потоке (сотни разом) может подрасти время выполнения, но корректность не пострадает.
- ✅ **Удаление блюда из заказа ДО закрытия**: безопасно по конструкции — открытые заказы не читаются вообще, только финальный состав на момент закрытия.
- ⚠️ **НЕ проверено (открытый риск)**: удаление блюда ПОСЛЕ того, как заказ уже был прочитан и записан к нам в базу (переоткрыли уже закрытый стол, убрали позицию, закрыли снова). Код сейчас только ДОБАВЛЯЕТ, никогда не удаляет и не пересматривает уже записанное — если такое произойдёт, в базе останется "призрачная" продажа. Насколько это реальный сценарий на практике — зависит от того, как заведение обычно исправляет ошибочно пробитое (если исправления всегда идут ДО закрытия — риска нет).
- ⚠️ **НЕ проверено**: расхождение часов между компьютером r_keeper и компьютером Sync Agent (могло бы сдвинуть понимание "что является новым").

## АРХИТЕКТУРА (обсуждено 17.08.2026) — от сырых продаж к расчётному остатку и автозаявкам

### Уточнение формулы — важная связка с уже решённой проблемой двойного учёта

**Продажи r_keeper — это ТА ЖЕ категория риска, что и ручные списания StockFlow**, не отдельная задача. QUSH рано или поздно тоже импортирует эти же продажи в StoreHouse официально — значит наивное "все продажи с момента снимка минус по времени" может задвоить учёт с тем, что QUSH уже занёс. Решение — **то же самое сопоставление по факту наличия в реальных расходных документах StoreHouse** (товар+количество, широкое окно, без точного сопоставления штука-к-штуке), что уже разобрано выше в разделе "Логика избежания задвоенного вычитания списаний". Продажи r_keeper и ручные списания StockFlow проверяются ОДНИМ и тем же механизмом, не двумя разными.

**Итоговая формула:**
```
расчётный остаток = последний точный remain StoreHouse (GRemns)
                     − Σ (продажи r_keeper с момента снимка, переведённые в сырьё через техкарты)
                     − Σ (одобренные списания StockFlow с момента снимка)
                     + Σ (из вычитаемого выше — то, что уже реально нашлось в расходных документах StoreHouse — не вычитаем повторно)
```

### Недостающее звено — маппинг "блюдо r_keeper → техкарта StockFlow"

Реальный пример вскрыл проблему: одно из блюд в тесте называлось `POT5` — внутренний код r_keeper, не человекочитаемое название. Сопоставлять с техкартой StockFlow по названию (как `match-product` для товаров) здесь ненадёжно.

**План**: отдельная таблица-связка `rk_dish_id` (уже есть в `rk_sales_history`) → `tech_card_id`. НЕ пытаться сопоставлять полностью автоматически (риск наврать с расходом сырья) — предлагать кандидатов по схожести, человек подтверждает один раз, дальше запоминается (та же логика `ai_match_cache`, что уже работает для товаров/техкарт в чате).

**Статус: не начато.** Логичный следующий шаг перед самим расчётом остатка — без маппинга расчёт вообще не запустится.

### Автоматические заявки на закупку — на основе понимания расхода товара

**Формулы (когда накопится история):**
```
средний дневной расход = Σ расход сырья (продажи блюд → техкарты) за последние N дней / N
дней до конца запаса = текущий расчётный остаток / средний дневной расход
рекомендуемое количество к заказу = средний дневной расход × (срок доставки + желаемый запас в днях) − текущий остаток
```

"Срок доставки" для конкретного товара — уже есть готовый источник: `query_purchase_pattern` (реальный интервал между закупками, уже реализовано в ИИ-чате).

**Честная оценка готовности:**
- Сейчас (17.08.2026) истории продаж через r_keeper накопилось на несколько тестовых позиций — недостаточно для осмысленного "среднего дневного расхода". Нужны недели непрерывной работы синхронизации.
- Архитектуру стоит закладывать сейчас, чтобы она сама заработала правильно, когда данных накопится — не откладывать проектирование, только сам запуск в производство.

**Решение по автономности (согласовано с планом "Jarvis" — постепенная автономность по цене ошибки):** ИИ должен **предлагать** заявки ("этот товар скоро закончится, рекомендуемое количество — Х"), а не создавать их автоматически без подтверждения. Ошибка в закупке — это реальные деньги, к этому применяется более высокая планка доверия, чем к подсказкам в чате.

### Согласованный порядок работы (17.08.2026)

Обсуждаем поэтапно, не бросаемся сразу писать код по всем пунктам разом:
1. Маппинг "блюдо r_keeper → техкарта" — без него ничего дальше не запустится.
2. Логика расчётного остатка (с учётом сверки по документам StoreHouse, не по времени).
3. Расчёт среднего расхода / прогноз "дней до конца запаса".
4. UI/механизм предложения заявок (не автосоздание).

## Проверка встроенного отчёта "Онлайн остатки" (17.08.2026) — полезно, но не заменяет свой план

Нашли в официальной документации: StoreHouse имеет ВСТРОЕННЫЙ отчёт **"Онлайн остатки"** (`StoreHouse Pro → Калькуляция и складской учёт → Отчёты → Онлайн остатки`, в клиенте `Sh.exe`), который считает остаток "на сейчас" с учётом продаж r_keeper — то, что мы пытались построить сами.

**Как работает (по документации):** читает продажи из SQL-базы r_keeper (не из XML — другой путь, "Путь 1", который мы в своё время отложили) → сам переводит проданные блюда в расход ингредиентов через GUID-сопоставление с комплектами (рецептами) StoreHouse → вычитает из текущих остатков по подразделениям.

**Проверено вживую пользователем — реально работает:**
- Отчёт открылся, показал реальные товары с количествами (включая настоящие продукты — молоко 79 литров, картошка фри 53 кг, не только упаковку).
- **Ошибок в нижней части окна нет** — значит, сопоставление блюд r_keeper с рецептами (комплектами) StoreHouse через GUID уже настроено и работает без сбоев.

**РЕШЕНИЕ (обосновано пользователем 17.08.2026): не использовать "Онлайн остатки" как основной источник для расчётного остатка StockFlow.**

Причина — принципиальный пробел: этот отчёт **физически не может знать про списания StockFlow** (это внешняя для StoreHouse система, данные о них появятся в StoreHouse только когда/если кто-то вручную занесёт документ). Наша формула требует вычитать ТРИ вещи (продажи r_keeper, списания StockFlow, и то, что уже реально попало в документы StoreHouse) — встроенный отчёт закрывает только одну из трёх. Продолжаем со своим планом (`sync-rkeeper-sales.js` уже реализован и протестирован), не отказываемся от него.

**Дополнительный риск, поднятый пользователем и подтверждённый:** даже сам remain StoreHouse (наша "точка отсчёта") может быть не полностью актуален — если кухня физически уже перевела сырьё в полуфабрикат (почистила, замариновала), а документ на внутреннее перемещение ещё не занесён в StoreHouse, remain будет показывать устаревшую картину (сырьё как нетронутое, полуфабрикат как ещё не появившийся). Это **та же категория риска**, что уже разобрана для продаж/списаний — не новая проблема, просто ещё один источник того же "документ существует физически, но не занесён в систему". Не решается технически, только организационно (дисциплина/скорость внесения документов на кухне) — принимается как факт, что расчётный остаток всегда будет ОЦЕНКОЙ, не точным фактом (что и планировалось изначально).

### Полезная находка на будущее — не терять из виду

Раз "Онлайн остатки" сопоставляет блюда r_keeper с комплектами StoreHouse через GUID БЕЗ ошибок — значит эта связка (`r_keeper dish GUID → StoreHouse комплект/товар`) уже где-то существует и обслуживается автоматически самим StoreHouse (вероятно, через обычный процесс импорта товаров/каталога, куда блюда попадают со своим GUID). **Стоит проверить, можно ли прочитать эту уже готовую связку через API** (например, есть ли у процедуры `Goods`/`GoodsItem` поле с внешним GUID, по которому можно найти нужный товар/комплект по known r_keeper dish GUID) — прежде чем строить СВОЙ интерфейс сопоставления "блюдо r_keeper → техкарта" с нуля вручную. Если такое поле есть — Этап 1 закрывается почти бесплатно, переиспользуя уже работающую связку StoreHouse, а не изобретая новую.

## ПРИНЦИП (сформулирован пользователем 18.08.2026) — что считать "правильной" техкартой

Раз у нас теперь есть синхронизация с r_keeper, критерий "какая техкарта правильная" должен определяться через РЕАЛЬНОЕ ИСПОЛЬЗОВАНИЕ, а не через сравнение названий/состава между дублями:

- **Для блюд, которые продаются через r_keeper**: единственная правильная техкарта — та, чей GUID совпадает с GUID блюда из r_keeper (`rk_guid` у товара ↔ `rk_dish_guid` у продажи). Не сравнение по названию, не по составу — по факту привязки к реально продающемуся блюду.
- **Для полуфабрикатов** (сами не продаются напрямую): правильный п/ф — тот, что реально встречается ингредиентом внутри состава настоящего (подтверждённого через GUID) блюда. Если нашёлся там — значит это точно нужная версия.

**Как это соотносится с уборкой дублей "Версия N" (18.08.2026):** удаление 571 карточки с ИДЕНТИЧНЫМ составом (по сравнению с "чистым" двойником) не противоречит этому принципу — содержание рецепта не потерялось независимо от того, какую из двух копий считать "источником истины". Для оставшихся спорных случаев (где состав между дублями РАЗЛИЧАЕТСЯ — тогда сравнение состава не помогает выбрать) — именно этот принцип (GUID/реальное использование) даёт чёткий критерий, которого раньше не было. Применять после подтверждения работы GUID-связки (см. выше).

## Продолжение поиска связки (19.08.2026) — поле "6\$ImportId" найдено, но пустое

После отказа гипотезы с `Guid` (см. выше) — нашли в официальной документации прямое упоминание: у товара, импортированного из r_keeper, есть отдельное поле **"Код r_keeper"** на вкладке "Основные параметры" карточки товара в клиенте StoreHouse (`Sh.exe`). Пользователь подтвердил — бухгалтер лично показывал это поле, оно точно существует и заполнено хотя бы у части товаров.

### Найдено в полной структуре процедуры Goods (через sh5struct)

Среди всех полей нашлось:
```
{"path":"6\\$ImportId","type":"tStrP","size":0,"isAttr":true,"caption":"Идентификатор для импорта"}
{"path":"6\\SDInd","type":"tUint16","size":2,"isAttr":true,"caption":"Индикатор срока хранения (за N дней)"}
```

"Идентификатор для импорта" — по названию очень похоже на искомое поле "Код r_keeper".

### Проверено вживую — результат отрицательный (пока)

Написан `probe-goods-importid.js` — переиспользует ТОЧНО тот же рабочий способ вызова `Goods`, что уже используется в продакшене (`fetchGoodsInGroup`, по группам через `GGroupsTree` + `Goods` с `head:'209'`), запросили дополнительно поле `6\$ImportId`.

**Результат на трёх ЗАВЕДОМО известных, реально продающихся через r_keeper товарах — `importId: null` у всех:**
```
BA5: sh_id=5783, importId=null
Картофель ФРИ 150гр: sh_id=1276, importId=null
Булочка б/л: sh_id=1679, importId=null
```

### Вывод и гипотеза на продолжение

Поле **найдено технически правильно** (путь подтверждён структурой), но обычный способ чтения (через `parseTable`, как для всех остальных полей) возвращает `null` — вероятная причина: у этого поля стоит специальная пометка **`"isAttr": true`** в структуре, в отличие от ВСЕХ остальных использующихся полей (`name`, `sh_id`, `Komplekt: Rid`, цены и т.д., у которых `isAttr` не установлен или `false`). Это, скорее всего, означает, что "атрибуты" (isAttr) — отдельная категория данных в API StoreHouse, требующая ДРУГОГО механизма извлечения значения (не через тот же основной запрос колонок), которую мы ещё не нашли.

**НЕ проверено:** является ли `null` реальным (у ЭТИХ конкретных трёх товаров поле правда не заполнено) или технической проблемой чтения (isAttr нужно запрашивать иначе). Не исключено, что нужен отдельный API-вызов специально для чтения расширенных атрибутов товара.

### Рекомендованные следующие шаги (для нового чата)
