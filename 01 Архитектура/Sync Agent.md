# Sync Agent

Node.js-программа, работает как Windows Service (через `nssm.exe`). **Код не в git-репозитории StockFlow** — отдельный проект, файлы передаются вручную.

## ⚠️ Важно: их ДВА, на разных компьютерах, с разными задачами

Раньше эта заметка описывала всё как один процесс — неточно. На деле в заведении **два компьютера**, на каждом свой экземпляр Sync Agent, они **не связаны друг с другом напрямую**, каждый решает свою половину обмена данными.

### Компьютер 1 — бухгалтерский (Unit99)

Старая, изначальная функция — направление **StockFlow → StoreHouse**:
- Скачивает готовые XML-файлы (списания/приёмки/инвентаризации) из Supabase Storage в локальные папки:
  ```
  C:\StockFlow\ToStoreHouse\WriteOff
  C:\StockFlow\ToStoreHouse\Suppliers
  C:\StockFlow\ToStoreHouse\Inventory
  ```
- Дальше человек **вручную** открывает файлы в StoreHouse и импортирует.
- Требует участия человека на каждый документ.

### Компьютер 2 — там же, где физически стоит StoreHouse Web API

Новая функция (добавлена 02–03.08.2026) — направление **StoreHouse → StockFlow**, полностью автоматически, без файлов:
- Служба `Sh5_webAPI_II_1`, слушает `https://localhost:9797` (самоподписанный сертификат — нормально для локальной сети).
- Пользователь StoreHouse `StockFlow` — доступ только на чтение нужных процедур (создан через SdbMan.exe).
- Реальная база StoreHouse — на **другом, третьем** компьютере в сети (IP `192.168.1.72`, порт 7771) — Web API тут просто "мост".
- Синхронизирует напрямую в Supabase (`sh_products`, `tech_cards`, `tech_card_ingredients`) — без участия человека.

**Их не нужно "соединять в одну систему"** — они вместе покрывают обе стороны обмена (что StockFlow отправляет в StoreHouse, и что забирает из него), просто исторически оказались на разных машинах, там, где физически было удобнее.

**На будущее:** если когда-нибудь понадобится, чтобы компьютер 1 тоже обращался к Web API — в его `.env` нужен не `localhost` (сработает только с самого компьютера 2), а реальный IP компьютера 2 в локальной сети.

## Расположение и файлы (компьютер 2 — API-синхронизация)

- `index.js` — точка входа, планировщик (интервалы скачивания/выгрузки), логирование.
- `sync-catalog-api.js` — синхронизация каталога товаров/техкарт через StoreHouse Web API (GGroupsTree/Goods/CmpDetails).
- `.env` — креды (`SH_API_URL`, `SH_API_USERNAME`, `SH_API_PASSWORD`, `SUPABASE_URL`, `SUPABASE_KEY` — это service_role/`sb_secret_...`, обходит RLS).

## Что делает (компьютер 2)

1. **Синхронизирует каталог** (`sync-catalog-api.js`, раз в сутки + сразу при старте): товарные группы → товары → полуфабрикаты → техкарты, эмбеддинги. Проверено на реальных данных — полная синхронизация 6000+ товаров и техкарт проходит успешно.
2. **Логирует** — параллельно в локальный файл `Logs\sync-agent.log` и в таблицу `sync_agent_logs` в Supabase (добавлено 02.08.2026).

## Что делает (компьютер 1)

1. **Скачивает** файлы из Supabase Storage (`storehouse-exports`) в локальные папки, см. выше.
   - Классификация по подпапкам (`Suppliers`, `WriteOff`, `Inventory`) — по содержимому XML или по имени файла (`classifyXml`). ⚠️ Приёмка (`Prihod_...`) классифицируется в папку **`Suppliers`**, отдельной папки "Приход" нет — контринтуитивно, но так есть.
   - После успешного скачивания файл **удаляется** из Storage и **регистрируется** в `Config/downloaded.json`, чтобы не скачивать повторно.
   - ⚠️ Имя файла приёмки строится **без времени**, только по дате+поставщику — повторные загрузки от одного поставщика в один день получат одинаковое имя и будут перезаписывать друг друга / не перескачиваться повторно (уже фиксированный риск, актуально при частом тестировании).

## Диагностические скрипты (одноразовые, не входят в основной код)

Использовались для нащупывания структуры StoreHouse Web API — можно повторно запускать при необходимости:
- `list-groups.js` — выводит все группы товаров (`GGroupsTree`) с иерархией.
- `probe-suppliers*.js` (v1–v5) — перебор названий процедур для списка поставщиков, закончилось на `UContractors`/`UContractor` — см. [[01 Архитектура/StoreHouse API|StoreHouse API]].

## Важные технические уроки

- **Edge Functions деплоятся отдельно от фронтенда** — через Supabase Dashboard/MCP, не через git push. Легко забыть и решить, что фикс "не сработал", хотя просто не задеплоен.
- **PowerShell при сборке JSON может "распаковывать" массивы с одним элементом** — если тестируете API через PowerShell, собирайте JSON-тело как обычную строку.
- **Кириллица в cmd.exe/PowerShell может выглядеть искажённой** даже если данные в порядке — проверяйте напрямую в Supabase, не по консоли Windows.
- **JS `\b` (граница слова) не работает на кириллице** — регулярки вида `/\bбар\b/i` никогда не сработают на чисто русском тексте. Использовать разбиение на слова через `.split(/[^a-zа-яё0-9]+/i)` и сравнение целых слов.
- **`let`/`const` в strict mode — temporal dead zone** — обращение до объявления кидает `ReferenceError`, роняя процесс целиком без единой строки лога, если это происходит на самом старте. Разбираться в первую очередь при "служба падает сразу после старта, ошибок в логе нет".
- **`.env`-креды НЕ печатать в чат целиком** — только first chars для проверки типа ключа при необходимости.
