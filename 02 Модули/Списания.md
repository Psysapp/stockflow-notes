# Модуль: Списания

Создание списания: `CreateWriteOffPage.tsx` / `CreateGroupWriteOffPage.tsx`. Список и выгрузка в StoreHouse: `WriteOffsPage.tsx`.

## Важное разделение по времени

- **При создании** (`CreateWriteOffPage`) — просто сохраняется исходная позиция (товар/п/ф, количество, единица, причина) в `write_offs.items`. **Раскрытия по техкарте на этом шаге НЕТ.**
- **При одобрении/выгрузке** (`WriteOffsPage`, кнопка "Обработка...") — вызывается `expandSemiFinishedItems` (раскрытие полуфабрикатов по техкарте), затем `generateWriteoffXml`, затем `uploadXmlToStorage`.

Это значит: в интерфейсе создания списания пользователь **не видит и не выбирает**, какая техкарта/рецепт будет использован для раскрытия — это решается полностью автоматически на следующем шаге, невидимо.

## Раскрытие полуфабрикатов (`expandSemiFinished.ts`)

Рекурсивное (любая глубина вложенности), с защитой от циклов (`MAX_DEPTH=6`, отслеживание цепочки). Допущение: 1л ≈ 1кг для сравнения весовых/объёмных ингредиентов в одной пропорции.

### Баг с дублями названий техкарт (найден и исправлен 03.08.2026)

В StoreHouse часто встречаются **несколько техкарт с одинаковым названием**, ссылающиеся на совершенно разные (иногда случайные) рецепты. Пример: "СОУС МЕКСИКАНСКИЙ П/Ф" без версии — рецепт мясного супа/солянки (хвосты говяжьи, язык), а "...Версия 0" — настоящий соус (сыр творожный, сливки, халапеньо).

**Найденная закономерность (подтверждена на 5+ реальных случаях):** версионированная карточка ("...Версия N" в названии) почти всегда правильная, безверсийный "тёзка" — случайный мусор/другое блюдо.

**Текущая логика выбора** при нескольких совпадениях по имени:
1. Отбросить помеченные "не использ..." (если после отбрасывания список не пуст).
2. Из оставшихся — предпочесть версионированные ("Версия N" в названии).
3. Если всё ещё неоднозначно — выбрать по наибольшему числу ингредиентов.
4. Всегда — явное предупреждение (`window.alert`, см. ниже) со списком найденных дублей.

⚠️ Первая версия фикса ориентировалась только на "число ингредиентов" — сработала на одном случае, но сломалась бы на обратном (свиная шея: правильная карточка — с 1 ингредиентом, неправильная — с 9). Приоритет "версия" оказался надёжнее.

### Известное ограничение (частично снято фиксом выше)

Раньше в хендовере значилось: *"у некоторых товаров привязан не тот комплект — нельзя обнаружить программно"*. Это оказалось **не совсем так** — см. [[03 Журнал/Расследование — барные техкарты]]: настоящая причина большинства таких случаев — не "плохие данные StoreHouse", а то, что наш код передавал в `CmpDetails` номер самого комплекта вместо номера его актуального периода. После фикса (`fetchCmpPeriodMap`, 03.08.2026) это должно решиться само при следующей синхронизации, без ручной правки в StoreHouse. Отдельно, для дублей по ИМЕНИ (разные ситуации) — фикс с приоритетом версии остаётся актуальным.

### Отдельная, ДРУГАЯ проблема: неполные техкарты

"СОУС ХАЛАПЕНЬО П/Ф" — единственная техкарта (без дублей), но в её составе указана **только соль** (0.001 кг). Это раздувает коэффициент масштабирования до абсурдных значений (спишется ~300г чистой соли вместо соуса). Не проблема кода — нужно дополнить рецепт в самом StoreHouse. Обсуждалась идея проверки "подозрительно мало ингредиентов" (≤1-2) — предложение сделано пользователю, ответ не получен, **не реализовано**.

## UX-момент: блокирующий `alert()`

Предупреждения о дублях/проблемах при раскрытии показываются через `window.alert()` — блокирует страницу до нажатия "Закрыть", кнопка позади в этот момент показывает "Обработка..." (может выглядеть как зависание, но это не баг — обработка продолжается штатно после закрытия). Предлагалось заменить на менее навязчивый UI — **не реализовано**, ждём решения пользователя.

## Единицы измерения

`convertToCanonicalUnit` — общая функция (перенесена в `xmlGenerator.ts`, переиспользуется приёмкой). Конвертирует г↔кг, мл↔л, вес↔объём (допущение 1г≈1мл). Возвращает `null` для несовместимых семейств (шт и т.п.) — раньше в списаниях просто подставлялось число как есть с чужой единицей (баг, исправлен 10.07.2026 для самого списания, независимо от сегодняшней темы дублей).
