# Модуль: ИИ-ассистент (главный экран)

`src/modules/tma/ai/AIChatPage.tsx` — первый экран после входа (`ROUTES.AI_CHAT`, редирект из роутера). Backend — Edge Function `hyper-service`.

## Модель

**`openai/gpt-oss-120b`** (заменена с `llama-3.1-8b-instant` 03.08.2026 — старая устаревает у Groq + регулярно выдумывала несуществующие в StockFlow понятия вроде "номер заказа"/"дата приготовления"). Бесплатный тариф Groq (без карты) покрывает и эту модель. `reasoning_effort: 'low'` — модель "рассуждающая", без ограничения была бы заметно медленнее.

## Архитектура

- **Чтение** (`query_stock`, `query_techcard`) — на сервере (service role, SELECT, org-scoped).
- **Запись** (`create_writeoff`, `create_task`) — сервер готовит `actions[]`, реальная запись — на клиенте под сессией сотрудника (RLS как обычно).
- Доступные инструменты зависят от роли.

## Сделано (03–06.08.2026)

- **`create_writeoff`** — сопоставляет товар через `match-product`, пишет в актуальную схему `write_offs.items[]` (было: писало текст напрямую в устаревшие плоские поля, товар всегда уходил `sh_id=0`).
- Системный промпт ужесточён — явный запрет придумывать несуществующие в StockFlow понятия.
- Запасной разбор, если модель пишет вызов функции текстом (`<function=...>`) вместо настоящего structured tool_call.
- Запасной вывод сырого результата инструмента, если модель не смогла сформулировать текстовый ответ (пусто → используем данные напрямую).
- **`query_stock`** — при нескольких похожих товарах ("свиная шея" — Товар vs П/Ф) показывает кликабельные кнопки-варианты вместо текстового списка/угадывания.
- **Живые запросы** — при точно определённом товаре чат реально ждёт (до 8 сек) свежий ответ от Sync Agent через процедуру `GRemns` (таблица `sync_agent_requests`), помечает "актуально прямо сейчас". Если не успел — честно показывает данные последней синхронизации.
- **`query_techcard`** — вместо пересказа состава текстом показывает кликабельную карточку-ссылку на настоящий `TechCardDetailPage` в приложении. Текстовое дублирование убрано.
- `current_stock`/`purchase_price` в `sh_products` теперь реально синхронизируются (отдельная задача, но напрямую делает ответы чата честными, а не фейковыми).

## Не доделано

- **`create_task`** — ни разу отдельно не тестировался после всех правок выше.
- Обсуждались, не реализованы: спросить про последнюю приёмку, голосовая маркировка (ждёт принтер).
- Живые запросы сейчас только для `query_stock` — механизм придётся расширять, если появятся другие "быстро меняющиеся" вопросы.
- Полный сквозной тест всех правок вместе (модель + кнопки + карточки + живые данные) в одном заходе ещё не проводился.

## Обучение на исправлениях (06.08.2026)

По идее пользователя (вдохновлено разговором с ChatGPT про способы "обучить" ИИ без дообучения модели) — реализовано **обучение через общую память сопоставлений** (`ai_match_cache`), ту же таблицу, что уже наполняют приёмка и списания:

- `query_stock` теперь СНАЧАЛА проверяет кэш по точному тексту запроса, и только если там пусто — ищет заново по словам.
- Когда сотрудник кликает один из кнопок-вариантов при неоднозначности — выбор записывается в кэш (`hyper-service`, обработчик `resolvedQuery`, поле `rawQuery` передаётся от сервера клиенту и обратно).
- Эффект общий на всё приложение: исправление в чате помогает приёмке и наоборот, и наоборот.

## Поиск теперь по словам, не по фразе целиком (06.08.2026)

Найдено на реальном тесте: техкарта "СОУС МАЙОНЕЗ ГОРЧИЦА П/Ф (шеф соус)" не находилась ни по "горчица майонез шеф соус" (другой порядок слов), ни по "шеф-соус" (дефис вместо пробела) — `query_stock` и `query_techcard` использовали обычный SQL "содержит подстроку целиком". Исправлено на "содержит ВСЕ слова, в любом порядке" — каждое слово отдельным `.ilike()`, Supabase объединяет через И. Разбивка слов — по пробелам И дефисам (`/[\s-]+/`).

## Сквозная проверка всех сценариев (06.08.2026)

Полный клик-тест через реальный интерфейс невозможен (нет инструмента для управления браузером/Telegram) — сделана **проверка кода вручную по каждому сценарию** + сверка с реальными данными в базе (SQL). Результат:
- `query_stock` (уверенное совпадение, неоднозначность), `query_techcard`, обучение на исправлениях — логически корректны, данные для тестов в базе есть.
- `create_task` — ни разу не тестировался, но структура данных и RLS-политики (`tasks`, `task_assignees`) проверены построчно, соответствуют коду.
- **Найден и исправлен реальный баг**: `create_writeoff` — если товар совсем не находится в каталоге, в списание записывалось `product_name = единица измерения` (например "шт") вместо настоящего названия, которое сказал сотрудник. Оригинальный текст нигде не передавался в `finalizeWriteoff` для fallback-случая. Исправлено — добавлен параметр `rawName` с явным default `'неопознанный товар'`.

## Смысловой поиск для техкарт (11.08.2026)

По ориентиру "Джарвис" (слой 1 — расширять зрение): у товаров (sh_products) уже давно есть смысловой поиск через эмбеддинги, у техкарт его не было вообще, только текстовый поиск по словам. Устранено:

- Новая колонка `tech_cards.embedding` + RPC `match_tech_cards_by_embedding` — та же схема, что у `sh_products`.
- Новая отдельная edge function `embed-techcards` — считает эмбеддинги порциями по 25 за вызов. Специально ОТДЕЛЬНАЯ функция, не расширение существующей `embed-catalog` — из-за путаницы с содержимым `embed-catalog` (см. ниже) не стали рисковать ломать рабочую логику для товаров/поставщиков.
- `query_techcard` в hyper-service теперь сначала пробует смысловой поиск, при неудаче (эмбеддинги не досчитаны или ничего не нашлось) — использует прежний надёжный поиск "по всем словам" как запасной вариант.
- В `sync-catalog-api.js` добавлен `runEmbedTechCardsUntilDone()`, вызывается в конце каждого цикла синхронизации (не только при изменении товаров — техкарты синхронизируются отдельным путём через `import-techcards`, не через этот цикл).

**Известная странность инструментов:** `get_edge_function` для слага `embed-catalog` стабильно возвращает содержимое `match-product`, а не реальную логику подсчёта эмбеддингов товаров. Причина не выяснена (возможно баг отображения, возможно исторически общий файл). Из-за этого решили НЕ трогать `embed-catalog` напрямую при добавлении аналогичной функциональности для техкарт — сделали отдельную функцию `embed-techcards`.

## Память об исправлениях распространена на техкарты (11.08.2026)

Та же логика, что уже работала для товаров (query_stock → ai_match_cache), теперь и для query_techcard:
- Клик по карточке техкарты среди НЕСКОЛЬКИХ похожих (не когда карточка одна — там уже уверенное совпадение) — записывает выбор в `ai_match_cache` (match_type='techcard') прямо с клиента (RLS на этой таблице разрешает любому участнику организации писать).
- `query_techcard` теперь сначала проверяет этот кэш, потом эмбеддинги, потом словесный поиск как последний резерв.

## Единая функция сопоставления товара (11.08.2026)

Обнаружена несогласованность: `query_purchase_pattern` сопоставлял товар СЛАБЕЕ, чем `query_stock` — только кэш + текстовый поиск по словам, без эмбеддингов. "Как часто мы заказываем X" мог не найти товар, который та же формулировка прекрасно находила в `query_stock`.

Исправлено — логика (кэш сопоставлений → смысловой поиск через эмбеддинги → уверенно/неоднозначно) вынесена в общую функцию `matchProductCandidates(supabase, orgId, rawQuery)` в hyper-service. Теперь `query_stock` и `query_purchase_pattern` используют ОДНУ и ту же, проверенную логику — не расходятся в качестве поиска.

## Найден и исправлен молчаливый баг в create_task (11.08.2026)

Целенаправленно проверил `create_task` на те же классы багов, что уже находили в `create_writeoff` (непроверенный результат вставки). Нашёл: результат вставки `task_assignees` вообще не проверялся — при неверном `member_id` (внешний ключ на `organization_members.id`, вставка проваливается ЦЕЛИКОМ, не частично) задача создавалась без единого исполнителя, но пользователь видел лживое "✅ Задача создана".

Исправлено — теперь проверяется результат, при сбое честное предупреждение "Задача создана, но не удалось назначить исполнителя — откройте задачу и назначьте вручную".

## Сопоставление товара в чате переключено на проверенную match-product (11.08.2026)

При проверке согласованности обнаружено: `matchProductCandidates` (используется в query_stock/query_purchase_pattern) — это простой порог косинусной близости эмбеддингов (0.72/0.45, подобраны на глаз). У приёмки и списаний уже давно есть намного более зрелая версия этой же задачи — `match-product` — которая не полагается на голый порог числа, а отдаёт узкую выборку кандидатов настоящей модели и спрашивает её решение напрямую. Там же уже исправлено несколько реальных багов на практике.

Вместо повторного набивания тех же шишек — `matchProductCandidates` теперь вызывает `match-product` как обычный HTTP-эндпоинт (с service role ключом в качестве авторизации). Кэш (`ai_match_cache`) остался как быстрый путь перед вызовом. Теперь "сколько X на складе" и "определи товар для накладной" используют ОДНУ и ту же логику принятия решения, не могут разойтись в качестве.
