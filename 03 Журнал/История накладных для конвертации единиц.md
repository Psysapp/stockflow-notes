# Идея: учиться на истории накладных StoreHouse (единицы измерения)

## Контекст

При приёмке накладной иногда единица в накладной ("рул", "уп") не совпадает с единицей товара в каталоге ("шт"), и точно пересчитать нельзя (см. [[02 Модули/Приёмка]]) — выгрузка останавливается, ждёт решения человека. Пользователь предложил (05.08.2026): раз накладные от поставщиков **повторяются**, можно **учиться** на уже принятых накладных — как в StockFlow, так и (что ценнее) **в самом StoreHouse**, где история приёмок велась ещё до StockFlow.

## Найденные процедуры (официальная документация, не угадывание)

- **`GDocs`** — список накладных за период (дата, поставщик, номер, тип документа). Полная спецификация подтверждена: `https://docs.rkeeper.ru/sh5/gdocs-spisok-nakladnyh-29196981.html`. Фильтр по типу документа — битовая маска (`1` = приходная накладная).
- **`GDoc0`** — состав ОДНОЙ конкретной накладной (вызывается по её Rid). Формат вызова подтверждён в примерах API: `{"head": "111", "original": ["1"], "values": [[docRid]]}`. Точная структура полей ответа — не задокументирована отдельной страницей, нужно смотреть через `sh5struct` вживую.
- Есть также готовый отчёт **"Отчёт по приходам"** в самом интерфейсе StoreHouse — судя по описанию, показывает ровно нужные поля (товар, **единица измерения, указанная в накладной**, количество) — подтверждает, что нужные данные в принципе существуют и доступны, просто нужно вытащить их через API, а не глазами из отчёта.

## План (после проверки структуры)

1. `GDocs` (тип=приходная) за длинный период (например, весь доступный) → список Rid накладных.
2. Для каждой — `GDoc0` → товар + количество + единица, как реально записано.
3. Строим таблицу "товар → единица, в которой его обычно принимают, и с каким коэффициентом к каноничной единице каталога" — по сути автоматически предзаполняем то, что раньше сотруднику пришлось бы вводить вручную один раз.
4. При новой приёмке — если единица не совпадает с каталогом, сначала смотрим в эту таблицу (реальная история StoreHouse), и только если там пусто — останавливаемся и просим человека, как сейчас.

## Параллельная быстрая идея (тоже не реализована)

Многие названия товаров уже содержат множитель прямо в тексте — например, "Пакет мусорный 120л ПНД 60х90 **(10шт/рул)** чёрный". Можно парсить такие множители регуляркой из названия — самостоятельно решает конкретные случаи без обращения к истории вообще. Быстрее в реализации, дополняет пункт выше, не заменяет.

## Статус (06.08.2026)

**GDocs и GDoc0 — подтверждены, работают.** GDocs дал 464 накладные за 90 дней. GDoc0 по конкретной накладной вернул реальный состав (пример: "Вино Хиромант 0,75", Rid=6172, Qnt=6, единица="0,75л").

**Но найдена более прямая зацепка, вероятно решающая задачу лучше, чем обучение на истории:** у единиц измерения в StoreHouse есть встроенный **коэффициент пересчёта относительно базовой единицы** (официально подтверждено документацией: `https://docs.rkeeper.ru/sh5/redaktirovanie-edinitsy-izmereniya-10814479.html`). Мы уже видели поле `CF` (Conversion Factor) в структуре `Goods` ещё 03.08 при поиске цен, но не использовали для единиц.

Нужна процедура **"Товар: множественные единицы измерения"** — список того, в каких единицах товар МОЖЕТ быть учтён + коэффициент для каждой. Кандидат — `GoodsMUnits` (видели в списке процедур 04.08, не проверяли). Если подтвердится — задача с несовпадающими единицами в приёмке решается напрямую из уже настроенных данных StoreHouse, без необходимости в обучении на истории накладных (GDocs/GDoc0 остаются полезными как запасной путь для товаров без настроенных множественных единиц).

Скрипт `probe-munits.js` подготовлен, ждёт запуска.
