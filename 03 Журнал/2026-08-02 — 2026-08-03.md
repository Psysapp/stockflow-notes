# Журнал изменений — 02–03 августа 2026

## 02.08.2026 — Приёмка накладных

- **Кандидаты сопоставления мешались между позициями батча.** Общий пул кандидатов на весь батч → раздельные списки на каждую позицию. (`match-product`)
- **`max_tokens` у Groq был фиксирован (2000)** → масштабируется от размера батча.
- **Главная причина ошибок сопоставления:** каталог из 6192+ товаров обрезался `.limit(5000)` в `DeliveryPage.tsx` → настоящая постраничная загрузка. Валидные точные совпадения/кэш отбрасывались как "несуществующие" из-за этого.
- **`upload-xml` не проверяла реальный результат записи** — теперь повторно перечитывает список файлов после записи, ведёт аудит в `xml_upload_log`.
- **Слияние позиций с одинаковым `sh_id` убрано** по явному запросу — каждая строка накладной теперь отдельная позиция.
- **Номер накладной (`f65`) содержал случайный `pointerId`** вместо `invoice_number` — исправлено.
- **Конвертация единиц измерения** добавлена в приёмку (переиспользована функция из списаний) + экран `confirm_upload` с паузой при несовместимых единицах.
- **Git-гигиена:** удалён случайно закоммиченный `.evn` с ключами, добавлен `.gitignore`, удалена папка `dist/` из репозитория.

## 02.08.2026 — Техкарты

- **Кухня/бар** — реализована автоматическая классификация по дереву групп StoreHouse (`resolveDepartment`), портируемая на новые организации. Результат: 1136 bar / 1468 kitchen из 2604 карт.
- **"Мусорные" ветки** (НЕ ИСП, Персонал, ОБРАБОТКИ, Хоз. товары) → `is_active: false`, 30 групп исключено.
- **Мониторинг Sync Agent:** таблицы `sync_agent_logs` и `xml_upload_log` — можно смотреть логи и аудит выгрузок прямо из Supabase, без пересылки файлов.

Подтверждено на 5 реальных примерах: 1000 островов, свиная шея, тесто на бельгийские вафли (безверсийный дубль оказался рецептом коктейля!), карамель, соус мексиканский (это тот самый "известное неисправимое ограничение" из старого хендовера — оказалось решаемым).

## 03.08.2026 (продолжение) — Массовая чистка техкарт по правилу версий

Применено новое правило видимости техкарт (по явному запросу, прямым SQL, без ожидания следующей синхронизации):
- Для каждого блюда: если есть "Версия 0" — показывать только её; иначе если есть "Версия 1" — только её; иначе (нет ни 0 ни 1) — скрыть **все** карточки этого блюда.
- **Важное открытие в процессе:** применённое ко всей базе, это правило **полностью стёрло видимость бара** (1136/1136 карточек) — оказалось, версионирование в StoreHouse практикуется **только на кухне**, у бара таких меток нет вообще. Откатили именно для bar (вернули is_active=true всем 1136), кухня осталась с применённым правилом.
- Итог: кухня 800 → 691 активных (после ещё одной чистки, см. ниже), бар — без изменений, 1136.
- **Не закреплено в коде `sync-catalog-api.js`** — при следующей синхронизации категория "kitchen" перезапишет is_active обратно в true для всех. Нужно доработать код (отложено до возвращения к компьютеру).

Отдельно скрыто **109 кухонных карточек типа "обработка продукта"** (напр. "БАКЛАЖАНЫ П/Ф" → "Баклажан", "БЕЛОК ЯИЧНЫЙ П/Ф" → "Яйцо куриное") — один ингредиент, совпадающий по сути с самим блюдом, просто с потерями на обработку. Проверены все 109 вручную на ложные срабатывания — не найдено ни одного.

## 03.08.2026 (продолжение) — Барные техкарты: масштабная проблема

При проверке бара после чистки обнаружено: **75% барных техкарт содержат состав от другого товара** (текила→индейка, вино→икра масаго, ром→перчатки и т.д.). Подробное расследование см. [[03 Журнал/Расследование — барные техкарты]]. Ведущая гипотеза (пользователя): Rid комплекта не уникален между складами кухня/бар, наш запрос `CmpDetails` не передаёт склад — сервер путает, откуда брать состав. Проверка подготовлена, не выполнена (ждёт компьютера).
