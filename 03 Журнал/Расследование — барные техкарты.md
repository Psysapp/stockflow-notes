# Расследование: барные техкарты собраны неправильно

## Симптом

Пользователь: "почти ни одна барная техкарта не собрана правильно". Проверка подтвердила — на случайной выборке 20 одноингредиентных барных карточек **75% содержат состав от совершенно другого блюда/товара**. Примеры абсурдных случаев:
- Текила → филе индейки
- Вино Соаве → икра масаго
- Ром → одноразовые перчатки (100 шт)
- "НАСТОЙКА ВИШНЯ РОЗМАРИН П/Ф" → лангустины, тесто катаифи, заправка на Кобб (реальный кухонный рецепт закуски)

Простые "наливные" позиции (водка/виски/коньяк по бренду) в среднем чаще корректны, но не гарантированно — тоже встречаются ошибки (см. пример с текилой выше).

## Проверено и исключено

- **Не баг нашего кода парсинга.** Цикл в `sync-catalog-api.js` (обработка `polufabrikaty`) структурно чист — `for...of` с `const`, свежий `goods` на каждую группу, никакой путаницы переменных между итерациями.
- **Не системная ошибка.** Если бы парсинг был сломан — ломалось бы всё одинаково. У нас смесь верных и неверных карточек — это не то, как ведёт себя баг в коде.
- **Ингредиенты в "неправильных" карточках — настоящие, используемые в других кухонных рецептах**, с разумными весами. Это не мусор, не выдумка — реальный чей-то рецепт, просто привязанный не туда.

## Ведущая гипотеза (пользователя, не проверена до конца)

**Кухня и бар — разные "склады"/подразделения в StoreHouse, и Rid комплекта (рецепта) может быть НЕ глобально уникален** — только в пределах склада. Наш вызов `CmpDetails` передаёт ТОЛЬКО Rid комплекта, без указания склада/подразделения. Если Rid действительно неуникален между кухней и баром — сервер может путать, откуда брать состав (скорее всего отдаёт с кухни, раз там данных сильно больше).

Косвенное подтверждение: в StockFlow уже заведено 4 локации (`storage_locations`): Кухня, Бар, Зал, Склад — организация реально мультискладская.

## Проверка (не выполнена, ждёт доступа к компьютеру)

Скрипт `probe-cmpdetails-warehouse.js` — запрашивает структуру `CmpDetails` через `sh5struct` (проверить, что реально означает второе поле — мы предполагали "дата", но не проверяли), плюс тестовый вызов на konkретном Rid=676 (komplekt "НАСТОЙКА ВИШНЯ РОЗМАРИН П/Ф"). Заготовлен, Rid уже вписан в скрипт — просто запустить.

## ПРОРЫВ (03.08.2026, вечер) — найдена вероятная настоящая причина

Пользователь предложил "пойти обратным путём" — открыть комплект 676 ("Настойка вишня, розмарин п/ф") напрямую в StoreHouse Pro (десктоп), не через API. **Результат: в самом StoreHouse состав правильный** — лимонная кислота, ягода с/м, сахарный сироп, водка Фабрикант, сахар. Это железно доказывает: **данные в StoreHouse корректны, проблема — в нашем API-запросе**, не в качестве данных клиента. Полностью меняет вывод предыдущих сессий ("это StoreHouse-проблема, руками не починить").

**Вероятная причина:** поле "1" в CmpDetails (то самое, куда мы передаём Rid комплекта) по алиасу называется **"RidPeriodCmp"** — то есть, судя по названию, это Rid КОНКРЕТНОГО ПЕРИОДА комплекта (у комплектов есть история пересчётов — видно на экране StoreHouse: "Период с: 01.05.2026", "Версия: 0"), а НЕ Rid самого комплекта. Мы всё время передавали туда master-Rid комплекта (676), а не Rid его актуального периода — для многих рецептов это, похоже, случайно совпадает/работает, но для отредактированных (несколько периодов в истории) — нет, и подставляется чужой период.

## ✅ РЕШЕНО (03.08.2026, поздний вечер) — настоящая причина найдена и исправлена

Гипотеза про "период" подтвердилась полностью. Через SdbMan (список ВСЕХ процедур сервера + просмотр исходника `CmpDetails`) нашли:
- Исходник `CmpDetails` подтвердил: поле "1" на входе действительно называется `RidPeriodCmp`.
- Процедура **`CmpVers`** ("Комплект: Версии") и особенно **`Cmps`** — без параметров отдаёт СРАЗУ ВЕСЬ каталог комплектов (3064 шт. на момент теста), включая поле `217\1` = `RidCmpPeriod` для каждого.

**Проверено на конкретном примере:** комплект 676 ("Настойка вишня, розмарин п/ф") → правильный период = **7793** (совсем другое число!). `CmpDetails(7793)` вернул состав, **точно совпадающий** с тем, что видно в StoreHouse Pro: лимонная кислота, специи, ягода с/м, шалфей свежий, сахарный сироп, водка Фабрикант, сахарный песок.

**Фикс внедрён в `sync-catalog-api.js`:** новая функция `fetchCmpPeriodMap()` запрашивает `Cmps` ОДИН РАЗ за цикл синхронизации, строит карту "Rid комплекта → Rid периода". `fetchCmpDetails` теперь переводит номер через эту карту перед вызовом `CmpDetails`. При отсутствии записи — откат к старому поведению (не роняет синхронизацию).

**Значение для проекта:** решает проблему для ВСЕХ организаций через чистый API, без ручных шагов (печати техкарт) — именно то, что нужно для автономного подключения новых заведений без ручного обучения каждого клиента. Главная находка сессии.

**Осталось сделать:** заменить файл на компьютере, перезапустить службу, дождаться полной синхронизации, выборочно перепроверить несколько техкарт (настойка, "Соус Мексиканский" и т.п.) — состав должен стать правильным.
