## 17.08.2026 — Настоящий баг: `sh_products.updated_at` был бесполезен

Обнаружено: `updated_at` у товаров показывал дату **первого** появления строки (много месяцев назад), не дату последнего обновления остатка — потому что `sync-catalog-api.js` никогда явно не проставлял его при upsert (а `DEFAULT now()` в базе срабатывает только при INSERT, не при UPDATE). Это критично для расчётного остатка — "точка отсчёта" была неверной. Исправлено, подтверждено на реальном товаре (мука: дата обновилась, остаток тоже реально менялся всё это время, просто дата рядом лгала).

## 17.08.2026 — Частое обновление остатков (`syncRemainsOnly`) — три раунда исправлений

**Идея:** не ждать раз-в-сутки полной синхронизации ради свежих остатков — отдельная лёгкая функция каждые 3 минуты, только `GRemns` (один запрос на всю организацию) + запись `current_stock`/`updated_at`.

Реализация потребовала три последовательных исправления реальных багов, найденных на практике (не гипотетических):
1. Первая версия — обычный `upsert()` уронил ВСЕ 6 пачек с ошибкой "null value in column name" (0 из 5209 записано).
2. Вторая попытка (предварительная проверка "существует ли товар") — тоже упала: `.select()` без пагинации молча ограничился 1000 строк из 6206 (лимит PostgREST по умолчанию).
3. **Настоящая причина:** обычный `upsert()` в PostgREST переписывает ВСЮ строку, включая непереданные поля (становятся NULL) — принципиально не годится для частичного обновления. Решение — хранimая функция `update_products_stock` в базе, делает настоящий `UPDATE` только нужных полей через `WHERE`, несуществующие sh_id просто не находятся, без единой ошибки.

**Статус на конец сессии: исправление №3 написано и отдано, ЕЩЁ НЕ УСТАНОВЛЕНО** (пользователь ждёт свободного компьютера).

## 18.08.2026 — Попытка найти GUID-связку "блюдо r_keeper → товар StockFlow" — НЕ УДАЛАСЬ (пока)

Гипотеза: поле `Guid` товара в StoreHouse (найдено через `sh5struct`, путь "4") совпадает с `guid` блюда из r_keeper (не `line_guid` — тот меняется каждый раз, `guid` должен быть постоянным). Добавлены колонки (`rk_guid` у `sh_products`, `rk_dish_guid` у `rk_sales_history`), собраны данные.

**Проверка показала: 0 совпадений из 139 уникальных проданных блюд.** Поле `Guid` товара — это собственный внутренний ID StoreHouse, не тот же GUID, что использует r_keeper.

**Найдена более многообещающая зацепка в официальной документации** (после того как пользователь остановил гадание по API-ответам и попросил свериться с документацией): у товара, импортированного из r_keeper, есть отдельное поле **"Код r_keeper"** на вкладке "Основные параметры" — судя по описанию, скорее числовой код (как наш уже собираемый `rk_dish_id`, например "3266"), не GUID. Технического имени поля в структуре API документация не даёт напрямую.

**Статус на конец сессии:** подготовлен `probe-goods-full-struct.js` (полный дамп структуры полей + все значения для конкретного известного товара) — **результат ещё не получен**, ждём запуска пользователем. Это ключевой открытый вопрос для продолжения — см. [[04 Задачи/Отложенные задачи]].
